Git 到底在做什么？
理解版本、分支和合并

这不是 Git 命令教程。你不需要记 git add、git commit 或 git push。在 Agent 可以完成代码操作的情况下，你真正需要理解的是：项目为什么可以保留历史、为什么可以同时修改、以及不同修改最后怎样重新汇合。

先理解一个核心想法

普通文件夹只告诉你“现在有哪些文件”。Git 还会记录这个项目是怎样一步一步变成现在这个样子的。

可以把 Git 理解为：项目的时间机器 + 多条并行修改路线。

因此，改坏了可以回到以前；两个人可以同时工作；Agent 也可以在不破坏当前稳定版本的情况下尝试修改。

五个核心概念

1. Repository · 仓库

一个项目以及它的版本历史。它不只是“装代码的文件夹”，还记录这个项目过去发生过什么。

2. Commit · 版本节点

项目在某个时刻的一次记录。可以把它理解成一个有编号的“存档点”。后面的版本都建立在前面的版本之上。

3. Branch · 分支

从某个版本节点分出去的一条独立修改路线。它允许新功能、实验或修复先在旁边进行，而不马上改变主线。

4. Pull Request · 合并请求

在 GitHub 上提出：这条分支已经产生了一组修改，现在希望把这些修改纳入另一条分支，通常是 main。

5. Merge · 合并

把两条修改路线重新汇到一起。合并完成后，主线同时拥有原来的历史和这次新增的修改。

一张图看懂 Git 的分支

假设 main 是当前认可的项目版本。项目走到 C 以后，我们想尝试一个新功能，于是从 C 分出一条 branch。

A ── B ── C ───────────── F      main
          \
           D ── E                 feature branch
                \
                 Pull Request
                      ↓
                    Merge
A–F 都是 commit。D、E 没有覆盖 C，而是在 C 的基础上形成另一条历史；最后再把它合回 main。

这就是 Git 最重要的能力之一：“修改项目”不等于“立刻覆盖当前版本”。

main→从某个版本分支→独立修改→重新合并

那什么是 Conflict？

如果两条分支修改的是不同地方，Git 往往可以自动把它们合在一起。

但如果两条路线同时修改了同一处内容，而且结果不一致，Git 就不知道应该保留哪一个。这就是 merge conflict（合并冲突）。

冲突不是 Git “坏了”，而是 Git 在说：这里存在两个互相矛盾的版本，需要有人——或者 Agent——做出判断。

Git 和 GitHub 不是一回事

Git

版本控制系统。

负责 commit、branch、merge 等底层机制。没有 GitHub，Git 本身也可以工作。

GitHub

围绕 Git 仓库建立的在线协作平台。

除了托管仓库，还提供账号权限、Issue、Pull Request、Review、Actions 等协作功能。

所以，当你在 GitHub 网页上看到 branch、commit、Pull Request，本质上是在通过 GitHub 操作和观察 Git 的版本历史。

Agent 会写代码，为什么还需要理解 Git？

因为“谁敲下代码”与“谁理解项目发生了什么”是两件不同的事。

Agent 可以替你创建文件、修改代码、提交 commit、建立 branch，甚至解决部分冲突。但当你看到下面这些信息时，仍然应该知道它意味着什么：

  • Agent 说“我创建了一个 branch”——说明它开了一条独立修改路线。
  • Agent 说“产生了 3 个 commits”——说明这次工作形成了 3 个可追踪的版本节点。
  • GitHub 出现一个 Pull Request——说明有一组修改正等待被合并。
  • 出现 merge conflict——说明两条修改路线在某处发生了矛盾。
  • 某个版本出问题——Git 的历史让项目有机会定位和回退。

你不一定需要亲手操作 Git，但你应该能看懂项目的版本结构。

最后只记住这些

Repository = 项目 + 历史 Commit = 一个版本节点 Branch = 一条独立修改路线 Pull Request = 请求把一组修改合回来 Merge = 两条路线重新汇合 Conflict = 两条路线在同一处发生矛盾

如果这六句话能理解，DM001 里需要的 Git 基础就已经够用了。剩下的具体操作，可以交给 Agent 完成。
