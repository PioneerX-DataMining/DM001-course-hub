不要背 Git 命令。
先看懂它的世界。

Git 的核心并不是 add、commit、push。真正重要的是一个很简单的模型：Git 把项目保存成一连串可以分叉、也可以重新汇合的版本快照。理解这张“历史图”，Git 的大多数概念都会自然出现。

01 · WHY VERSION CONTROL

先从一个最普通的问题开始

假设你在做一个项目。今天改了一版，明天又改了一版；有时新版本变差了，于是你想回到昨天。最原始的办法，是不断复制文件夹：

版本控制首先解决的不是“怎么写代码”，而是：项目如何保留可信的历史。

版本控制系统（Version Control System, VCS）做的第一件事，就是记录一个项目随时间发生的变化，让过去的状态可以被找回来。Git 是今天最常用的分布式版本控制系统之一。GitHub 对 Git 的介绍也是从“记录项目变化历史”开始。

所以先记住：Git 不是代码编辑器。
它是项目的“历史系统”。
02 · SNAPSHOTS

Git 怎么记住历史？——不是“改了几行”，而是一张张快照

这是理解 Git 最关键的一步。官方 Pro Git 特别强调：Git 在概念上把数据看成一连串项目快照（snapshots）。每次保存一个版本时，可以把它想象成给整个项目拍了一张照片。

“快照”是心智模型。Git 的实际存储会通过内容寻址与复用避免无意义的重复。
Commit 是什么？ 一次 commit，就是把“这个时刻的项目状态”正式放进历史里，并附上作者、时间、说明以及它前一个版本是谁。
03 · HISTORY

快照一个接一个，就形成了项目历史

每个 commit 不只是一个孤立的存档点，它还知道自己的父 commit（parent）。于是很多 commit 连起来，就形成了一张历史图。

main 并不是“所有文件的另一个副本”。它只是指向当前主线最新 commit 的一个名字。

这时，一个比“Commit = 存档点”更准确的理解出现了：Git 的核心其实是一张 commit 图。每个节点是一次项目快照，边表示版本之间的前后关系。

04 · BRANCHES

Branch 不是复制项目——它只是一根会移动的指针

这是很多初学者最容易误解的地方。创建 branch 时，Git 并不会把整个项目复制成第二份。按照 Pro Git 的定义，branch 本质上只是一个指向某个 commit 的轻量、可移动指针。

✕ 容易产生的误解Branch = 把整个项目复制一份，然后在副本里修改。
✓ 更准确的理解Branch = 给某个 commit 放一个名字；之后新的 commit 会让这个名字继续向前移动。
从 C 之后，main 和 experiment 各自产生新的 commit，于是项目历史发生“分叉”。这就是 branching。
Git 的“分支”之所以强大，是因为它不是复制文件，
而是允许一张历史图同时长出多条路线。
05 · MERGE

分出去之后，怎么重新回来？—— Merge

如果实验路线最后值得保留，就需要把两条历史重新整合。Git 会寻找它们的共同祖先，并尝试把两边的变化组合起来。Atlassian 的 Git 教程把 merge 概括为：把一段分叉的历史重新放回统一历史。

典型的三方合并会产生一个新的 merge commit，它有两个父 commit：两条历史在这里重新汇合。

那 Conflict 又是什么？

Git 能自动判断很多合并。例如一条分支改标题，另一条改图片，通常可以自动组合。但如果两条分支都修改了同一处内容，而结果不同，Git 就无法替人决定“哪个才对”。这时才叫 merge conflict。

可以自动合并

main：修改首页标题
branch：增加一张新图

修改互不矛盾 → Git 可以组合。

产生冲突

main：标题改成“数据挖掘”
branch：同一标题改成“智能数据分析”

同一位置两种答案 → 需要判断。

Conflict 不是“Git 出错了”。 它准确地告诉你：历史里出现了两个 Git 无法自动替你选择的答案。
06 · GIT ≠ GITHUB

最后再把 GitHub 放进来

到这里，其实 Git 已经讲完了。Git 本身就能在一台电脑上保存 commit、建立 branch、合并历史。GitHub 是建立在 Git 之上的网络协作平台。

Git 是版本控制机制；GitHub 是托管 Git 仓库并增加在线协作能力的平台。Pull Request 是 GitHub 的协作概念，不是 Git 本身的一种对象。
Repository

项目文件 + Git 历史。

Pull Request

GitHub 上把一条分支的修改拿出来比较、讨论、检查并请求合并的协作页面。

Issue / Review / Actions

这些是 GitHub 围绕 Git 增加的项目管理、评审和自动化能力。

07 · IN AN AGENT WORKFLOW

Agent 在操作，但你看到的仍然是这张图

在 DM001 里，很多 Git 操作可以由 Agent 完成。学生没有必要背命令，但看到下面这些词时，应该知道项目历史发生了什么：

Agent 说…
你应该理解成…
“做了一个 commit”
历史图上多了一个版本节点。
“建了 branch”
从某个历史节点开始了一条独立路线。
“开了 PR”
GitHub 正在比较两条路线，并准备讨论是否把它们合起来。
“有 conflict”
两条历史在同一处给出了互相矛盾的修改，需要判断。
“merge 完成”
两条历史已经重新汇入同一条项目历史。

Agent 可以替你操作 Git，
但你至少要能读懂 Git 的历史图。

60-SECOND RECAP

如果只记六句话

Git记录项目如何从过去一步步变成现在。
Commit一次正式保存的项目快照，也是历史图上的一个节点。
HistoryCommit 通过父子关系连接起来，形成项目的版本历史。
Branch不是项目副本，而是指向 commit 的一根可移动指针。

GitHub把 Git 仓库放到网络上，再加上 PR、Issue、Review、Actions 等协作层。
